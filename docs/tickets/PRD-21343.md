## Product design

### Goals / Non-goals

- **Goal**: expose DigitalOcean's Serverless Inference model catalog and core inference operations (chat, embeddings, image generation) as MCP tools, so a connected agent can list available models and run inference against them through the MSPbots Agent Platform.
- **Goal**: standard MSPbots connector experience — Library card, credential connect form, `tools/list`-driven tool table, per-tenant encrypted header-scoped credential delivery, gateway-side audit log (platform-provided, not built here).
- **Non-goal**: Dedicated Inference (GPU-backed instance provisioning/lifecycle management, `/v2/dedicated-inferences*`) — a different, infrastructure-provisioning API, not a "model catalog"; not requested by this ticket's title.
- **Non-goal**: the Anthropic-style `/v1/messages` endpoint, audio speech, video generation, batch inference, agent inference, the `/v1/responses` and `/v1/systemone`/`/v1/async-invoke` endpoints — see Decisions made by DEV01 for why these are cut from v1.
- **Non-goal**: Apps, Kubernetes (DOKS), and Networking resource groups — covered by sibling tickets PRD-21338, PRD-21344, PRD-21345 respectively, in the same shared repository.

### 4. Solution (user-visible behavior)

#### 4.1 Main flow

1. A tenant admin connects "DigitalOcean" in the Agent Platform Library (or adds the Inference capability to an existing DigitalOcean connection, depending on how PRD-21338's connector registration lands — both tickets share one vendor registration, see Risks & dependencies), entering a DigitalOcean Personal Access Token or Model Access Key into the credential form.
2. An agent calls `tools/list` and sees the Inference tools alongside whichever other DigitalOcean resource-group tools have landed, each with a one-line description.
3. The agent calls `digitalocean_inference_list_models` and gets back the catalog of models currently available on the account (id, creation time, owner).
4. The agent calls `digitalocean_inference_create_chat_completion` (or `_create_embedding` / `_generate_image`) naming one of the catalog's model ids, and gets back the generated result (assistant reply / embedding vector(s) / generated image(s)) plus usage accounting.

#### 4.2 Interface & interaction changes

No MSPbots UI changes — this is an MCP connector; its only user-facing surface is the Agent Platform's generic connector Library/credential-form/tool-table UX (already shipped, described in wiki above) and the agent-facing tool descriptions themselves (see Tech design § Tool design).

#### 4.3 Edge cases & errors

- Missing credential header → the agent sees a clear 401 naming the required header; DigitalOcean is never called.
- Unknown/invalid model id passed to an inference tool → DigitalOcean's own validation error is surfaced verbatim in a structured error, not swallowed or turned into a generic failure.
- Rate limiting (DigitalOcean 429) → the connector retries a bounded number of times with backoff honoring `Retry-After`; if still rate-limited, the agent sees a structured `rate_limited` error rather than a bare timeout.
- Empty/short input (e.g. a single-word chat prompt, a one-item embeddings array) → passed through normally; DigitalOcean's own API has no documented minimum beyond non-empty.
- Large input (long chat history, large embeddings batch, high `n` on image generation) → DigitalOcean's own request-size/parameter limits apply (e.g. `n` capped at 10 for image generation per its docs) and surface as DigitalOcean's own validation error.

#### 4.4 Permissions & multi-tenancy

Every inference tool call is scoped to the DigitalOcean token carried in that request's credential header; one MCP process serves many tenants concurrently, and no tenant's token, model list, or generated content is ever visible to another tenant's request — this is a hard platform-level requirement (SOP §3.3/§3.4: `contextvars`-scoped credential per request, no global/module-level state), not something this design can soften. A DigitalOcean token's own scope (which models/features it can call) is entirely controlled by the tenant in their own DigitalOcean account; this connector does not add a client-side permission layer on top.

### 5. Impact

New connector; no existing MSPbots users, data, or configuration are affected. No migration. The only other party affected is whichever of PRD-21338/21344/21345 merges around the same time into the same shared repository — see Risks & dependencies for how overlap is handled.

### 6. Acceptance criteria

- **AC1**: Given `tools/list` is called with a valid credential header, When it completes, Then it returns exactly 4 Inference tools (`digitalocean_inference_list_models`, `digitalocean_inference_create_chat_completion`, `digitalocean_inference_create_embedding`, `digitalocean_inference_generate_image`), each with a one-line description ≤ 100 characters.
- **AC2**: Given a `tools/call` request that is missing the `X-DigitalOcean-Api-Token` header, When any Inference tool is invoked, Then the response is HTTP 401 and the body lists the required header name — the request never reaches DigitalOcean's API.
- **AC3**: Given a valid token, When `digitalocean_inference_list_models` is called, Then it returns the account's available models (id, created timestamp, owner) from DigitalOcean's `GET /v1/models`; the tool is annotated `readOnlyHint: true`.
- **AC4**: Given a valid token and a catalog model id with a chat message list, When `digitalocean_inference_create_chat_completion` is called, Then it returns the assistant's reply content, finish reason, and token usage; Given an unknown/invalid model id, Then DigitalOcean's own error is surfaced as a structured error carrying DigitalOcean's message, not a generic failure or a 500.
- **AC5**: Given a valid token and input text (a single string or an array of strings), When `digitalocean_inference_create_embedding` is called, Then it returns one embedding vector per input plus token usage.
- **AC6**: Given a valid token and a text prompt, When `digitalocean_inference_generate_image` is called, Then it returns the generated image(s) (as returned by DigitalOcean) and, when present, DigitalOcean's revised prompt; the tool's description states it is not read-only (it creates new content and consumes the tenant's DigitalOcean quota).
- **AC7**: Given DigitalOcean returns HTTP 429, When any Inference tool is called, Then the connector retries with backoff honoring `Retry-After` within the SOP's bounded retry budget; if still rate-limited, the agent sees a structured `rate_limited` error, not a bare timeout.
- **AC8**: Given DigitalOcean returns HTTP 401 for an upstream-invalid token (as opposed to a missing MSPbots header, AC2), When any Inference tool is called, Then the agent sees a structured `unauthorized` error distinguishable from AC2's missing-header 401.
- **AC9**: Given two concurrent `tools/call` requests carrying two different tenants' `X-DigitalOcean-Api-Token` values, When both complete, Then neither response contains data retrieved using the other request's token — verified by a concurrency test asserting no shared mutable state keyed only by in-process globals.
- **AC10**: Given the repository's `README.md`, Then it documents the `X-DigitalOcean-Api-Token` header (purpose, how to obtain either a Personal Access Token or a Model Access Key), lists all 4 Inference tools in its tool table, and its "MSPbots Connector" section is byte-for-byte identical to `~/.claude/skills/vendor-mcp-development/reference/readme-connector-section.md`.

## Tech design

### 1. Conclusion

Build a new Python 3.12 + `uv` + FastMCP service module within `MSPbotsAIFramework/digitalocean-mcp` (second ticket to add code to this still-empty repo) implementing 4 MCP tools against DigitalOcean's public Serverless Inference REST API (`https://inference.do-ai.run`). One `httpx.AsyncClient` per request scoped via `contextvars`; credentials come from the single Header `X-DigitalOcean-Api-Token` (reused from PRD-21338's design, see § Decisions made by DEV01), forwarded as `Authorization: Bearer <token>` on every outbound call; nothing cached across requests.

### 3. Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| Mirror all 12 Serverless Inference endpoints 1:1 as tools | One tool per DO operation (models, chat, messages, embeddings, images, audio, video×3, systemone, responses, async-invoke, batch×7, agent) | Simplest mapping, no judgement calls | ~20 tools from this ticket alone — blows the repo's already-tight ≤20 ceiling (shared with Apps' 18) by itself; floods `tools/list` with rarely-used or duplicate-capability operations (e.g. `/v1/messages` duplicates `/v1/chat/completions`) | Rejected — violates SOP §2 and makes the cross-ticket tool-budget problem (Open Questions) far worse |
| 4 tools: catalog + chat + embeddings + images | Cover the "model catalog" ask literally (listing) plus the three most broadly useful generative operations | Matches the ticket's own title ("Model Catalog"); keeps this ticket's contribution to the shared tool budget modest; covers the overwhelming majority of real agent use cases (browse models, generate text, embed text, generate images) | Cuts audio/video/batch/agent/responses/messages from v1 — a real scope decision, recorded and open for a follow-up ticket if ever needed | **Chosen** |
| 1 tool only (catalog listing) | Just `list_models`, no inference execution | Smallest possible footprint | Doesn't actually let an agent *use* a cataloged model — "browse but can't act" is a materially worse agent experience and arguably doesn't satisfy "live access" from the ticket's own wording | Rejected — too narrow to be useful |

Selection order followed: no existing MSPbots implementation to reuse (nothing in this repo); no suitable open-source library to wrap (this is a thin, well-documented REST API — a hand-rolled `httpx` client is simpler and more auditable than pulling in a generic OpenAI-compatible SDK, which would also pull in unrelated surface area); hand-written client chosen as the only reasonable option, consistent with PRD-21338's identical choice for Apps.

### 5. Data & API contract

Upstream base URL: `https://inference.do-ai.run`. Auth: `Authorization: Bearer <token>` (DigitalOcean accepts either a general Personal Access Token or a dedicated Model Access Key in this header — both forwarded identically, no code-level distinction needed).

**`digitalocean_inference_list_models`** → `GET /v1/models`
```json
// response (200)
{
  "object": "list",
  "data": [
    {"id": "llama3.3-70b-instruct", "object": "model", "created": 1730000000, "owned_by": "digitalocean"}
  ]
}
```

**`digitalocean_inference_create_chat_completion`** → `POST /v1/chat/completions`
```json
// request
{"model": "llama3.3-70b-instruct", "messages": [{"role": "user", "content": "..."}], "max_tokens": 512, "temperature": 0.7}
// response (200)
{
  "id": "chatcmpl-abc123", "object": "chat.completion", "created": 1730000000, "model": "llama3.3-70b-instruct",
  "choices": [{"index": 0, "message": {"role": "assistant", "content": "..."}, "finish_reason": "stop"}],
  "usage": {"prompt_tokens": 10, "completion_tokens": 20, "total_tokens": 30}
}
```

**`digitalocean_inference_create_embedding`** → `POST /v1/embeddings`
```json
// request
{"model": "qwen3-embedding-0.6b", "input": ["text one", "text two"]}
// response (200)
{"object": "list", "model": "qwen3-embedding-0.6b",
 "data": [{"object": "embedding", "index": 0, "embedding": [0.0123, -0.0456]}],
 "usage": {"prompt_tokens": 6, "total_tokens": 6}}
```

**`digitalocean_inference_generate_image`** → `POST /v1/images/generations`
```json
// request
{"model": "openai-gpt-image-2", "prompt": "a red bicycle", "n": 1, "size": "1024x1536", "output_format": "png"}
// response (200)
{"created": 1730000000, "data": [{"b64_json": "iVBORw0KG...", "revised_prompt": "A red bicycle, studio lighting"}],
 "size": "1024x1536", "quality": "auto", "output_format": "png"}
```

**Error responses** (documented by DigitalOcean for this API group):
```json
// 401 — upstream-invalid token
{"id": "unauthorized", "message": "Unable to authenticate you."}
// 429 — rate limited
{"id": "too_many_requests", "message": "API rate limit exceeded."}
// 500 — server error
{"id": "server_error", "message": "Unexpected server-side error"}
```
DigitalOcean's docs do not give a documented shape for 400-class validation errors (invalid model id, malformed input) beyond the three above; this design passes through whatever `id`/`message` DigitalOcean actually returns under the mapped structured code, falling back to a generic `invalid_argument` by HTTP status (400→`invalid_argument`, 404→`not_found`) when `id` is absent — flagged as an assumption to verify against the real API during development (SOP A5's placeholder-credential test only exercises the 401 path; the exact 400 shape needs a real or sandbox call during the dev leg, not blocking this design).

**Error envelope** (SOP §4, MSPbots side, same for all 4 tools):
```json
{"error": {"code": "invalid_argument", "message": "<DigitalOcean's own message>", "retryable": false}}
```
Codes used: `not_configured` (missing Header), `unauthorized` (bad/missing upstream token), `invalid_argument` (bad model id or malformed input), `not_found` (unlikely for this API group, kept for consistency), `rate_limited` (429, `retryable: true`), `upstream_error` (5xx after retries exhausted, `retryable: true`).

**Backward compatibility**: new connector, no prior contract to break.

### 6. Key flow / sequence

```
Agent (tenant) --tools/call(digitalocean_inference_create_chat_completion, Header: X-DigitalOcean-Api-Token)--> Gateway
  --HTTP, Header forwarded--> digitalocean-mcp /mcp
    middleware: read Header -> ContextVar; missing -> 401 (AC2)
    tool: validate args -> inference/client.py
      -> builds Authorization: Bearer <token> from ContextVar
      -> POST https://inference.do-ai.run/v1/chat/completions
      -> 200: map response to tool result
      -> 429: retry w/ backoff honoring Retry-After, else rate_limited (AC7)
      -> 401: unauthorized (AC8)
      -> 400/404: invalid_argument / not_found, DO's message passed through (AC4)
<-- tool result (or structured error) <-- Gateway <-- Agent
```

### 7. Non-functional

- **Idempotency & concurrency**: `list_models` is naturally idempotent (read-only). Chat/embedding/image generation are inherently non-idempotent (each call may produce a different generated result, consumes quota) — no retry-as-idempotent assumption is made for successful calls; retries only apply to transport-level failures (429/5xx) before any response body is returned, never after a 200.
- **Performance**: `list_models` has no pagination in DigitalOcean's own API (SOP A4's list-pagination guidance doesn't apply — there's nothing to paginate); chat/embeddings/image responses are returned as-is (DigitalOcean already bounds image count via `n` ≤ 10 and `max_tokens` on chat); one `httpx.AsyncClient` reused per process (connection pooling), never shared tenant data across requests — only the transport is shared, credentials are per-request.
- **Security**: credentials never leave the request's lifetime — no logging of the token, no writing it to disk/env/cache; `gitleaks detect` run before delivery (SOP §11). No destructive tools exist in this ticket's scope (all 4 are read or generate-type calls), so SOP's destructive-tool safeguards (explicit id, no bulk operations) don't apply here — flagged explicitly rather than silently omitted.
- **Multi-tenant isolation**: `contextvars.ContextVar` scopes the credential per request (set in middleware, `reset()` in `finally`); no module-level or global mutable state holds tenant data between requests (AC9); the `httpx.AsyncClient` instance carries no auth state — `Authorization` is attached per-outbound-call from the context var.
- **Observability**: structured logs include tool name, DigitalOcean operation, model id when present, outcome, latency; explicitly never log the token header value, full chat message content, or generated image bytes (tenant content, not just tenant secrets).

### 12. Decisions made by DEV01

No one was available to ask (unattended design leg); these are the first-version scope and shape calls this design made on its own, each with the alternative considered:

- **Tool scope: catalog + chat + embeddings + images (4 tools), not all 12 Serverless Inference endpoints** — matches the ticket's own title ("Model Catalog": browse + use), keeps this ticket's contribution to the already-tight shared repo tool budget modest. Alternative not chosen: mirror all 12 endpoints as tools (rejected — see § Option analysis).
- **Cut `/v1/messages` (Anthropic-style chat alias)** — it duplicates `/v1/chat/completions`'s capability (generate a chat reply) in a different wire format; adding both doubles tool-list surface and maintenance for zero new agent-visible capability. Alternative: add both — rejected as pure duplication.
- **Cut audio speech, video generation, batch inference, agent inference, `/v1/responses`, `/v1/systemone`, `/v1/async-invoke`** — none of these are "model catalog" in the sense the ticket's title uses, and each adds meaningfully different request/response shapes (audio/video are async job-based, batch is a submit-then-poll pattern) that would roughly double the implementation and test surface for capabilities nobody has asked for yet. Alternative: include them now — rejected; add as a follow-up ticket if a real need is named.
- **Cut Dedicated Inference (`/v2/dedicated-inferences*`, GPU instance provisioning)** — this is an infrastructure lifecycle-management API (create/resize/delete a hosted-model instance), not a "catalog" of models to call; it's a different enough capability (and different enough risk profile — it provisions billable infrastructure) that bundling it into "Model Catalog" would misrepresent what this ticket's tools do. Alternative: include it — rejected as out of the ticket's named scope; would warrant its own ticket/title if wanted.
- **Credential header: reuse `X-DigitalOcean-Api-Token` from PRD-21338's design rather than inventing a second header for Inference** — DigitalOcean's own docs confirm a general Personal Access Token authenticates the Serverless Inference API (as an alternative to a dedicated, narrower Model Access Key); since this repo's four resource-group tickets will register as one connector (per the admin's own "shared repo" framing), one credential header keeps the connector to one credential form in the platform's Library UI instead of fragmenting into up to four tokens for what is, in DigitalOcean's own account model, a single account. Alternative: a dedicated `X-DigitalOcean-Inference-Key` header scoped to Model Access Keys only — rejected because it would force tenants to create and manage a second credential for one DigitalOcean account, and because a general PAT already works for this API per DigitalOcean's own docs.
- **Tool naming: `digitalocean_inference_<verb>_<resource>`** — follows PRD-21338's already-decided `digitalocean_<group>_<verb>_<resource>` scheme (its own design records this as chosen specifically because the repo will grow sibling tool groups). Alternative: flat `digitalocean_<verb>_<resource>` — not chosen, for the same collision reason PRD-21338 already rejected it (e.g. a future Kubernetes `list_models` equivalent for GPU node pools would collide with this ticket's `list_models` without the group segment — resolved here as `digitalocean_inference_list_models`).
- **Module layout: assumed `src/digitalocean_mcp/inference/` subpackage** — no code exists yet to confirm this against; chosen so this ticket's files don't collide with whatever PRD-21338 (or Kubernetes/Networking) names its own files, on the assumption a per-group subpackage is the natural shape for a 4-domain shared service. Alternative: flat `src/digitalocean_mcp/` with per-group filename prefixes (e.g. `inference_client.py`) — not chosen, but not strongly rejected either; whichever ticket's dev leg lands first effectively decides this, and later tickets should follow suit rather than re-litigate it.

To change any of these, say so in a comment and move the ticket back to 5b - ready for groom.
