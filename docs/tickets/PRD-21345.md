The ticket is a short Conduit plug-in blurb (not a detailed spec): "DigitalOcean Networking is a Conduit plug-in. Connect it to give Claude, ChatGPT, Cursor, or any MCP-compatible AI live access, with credentials encrypted and every action logged. Link: https://conduit.wyre.ai/plugins/digitalocean-networking". Per the established pattern for these Conduit-sourced tickets (the linked page is a generic marketing template, not vendor-specific API detail — same conclusion PRD-21338 and PRD-21343 reached comparing it against DigitalOcean's own docs), the real scope comes from matching the product name to DigitalOcean's actual public API surface, not from the link. ## Product design

### Goals / Non-goals

**Goals**
- Give an Agent Platform tenant, once connected, the ability to manage the four DigitalOcean networking resource groups most commonly needed to put an app or droplet on a secure, addressable network: VPCs (incl. VPC peering), Firewalls, Domains/DNS, and Load Balancers.
- Every write/destructive tool call must act only on an explicitly supplied resource id (vpc id, firewall id, domain name, load balancer id, peering id, domain record id) — no name-based matching, no "do this to all my VPCs/firewalls/..." bulk tools.
- Standard MSPbots connector experience: shows up in the Library with a credential (API token) connect form, `tools/list` enumerates the tools with one-line descriptions, each tool call is scoped to the tenant whose Header carried the token.

**Non-goals (this ticket)**
- The other DigitalOcean resource-group tickets in the same shared repository: Apps (PRD-21338), Inference Model Catalog (PRD-21343), Kubernetes/DOKS (PRD-21344).
- Within "Networking" itself, the following DigitalOcean tag groups are deliberately deferred to a follow-up (see Tech design § Option analysis and § Decisions made by DEV01 for why each one, individually): Certificates, Reserved IPs / Floating IPs (+ their Actions sub-resources), Reserved IPv6 (+ Actions), CDN Endpoints, VPC NAT Gateways, VPC Routes `[Public Preview]`, VPC Subnets `[Public Preview]`, BYOIP Prefixes, Partner Network Connect, Regions.
- Discrete "add/remove droplet", "add/remove tag", "add/remove forwarding rule" tools for Firewalls and Load Balancers — DigitalOcean's own whole-object `PUT` update already covers changing those arrays; see Tech design § Decisions made by DEV01.
- OAuth-based auth — DigitalOcean's networking APIs use the same single bearer token as Apps and Inference, so there is no authorization-code flow to support.
- A UI. This is a backend MCP connector; the only user-facing surface is the Agent Platform's existing generic connector chrome (Library card, connect form, tool list), which this ticket does not change.

### Acceptance criteria AC1..AC17

- **AC1**: Given the connector is running and a client sends `tools/list`, Then the response includes all 17 `digitalocean_networking_*` tools (see Tech design § Data & API contract for the full list), each with a description whose first line is ≤ 100 characters and whose full text is ≤ 500 characters, and each annotated with the correct `readOnlyHint`/`destructiveHint`/`idempotentHint` for its operation.
- **AC2**: Given a `tools/call` request that is missing the `X-DigitalOcean-Api-Token` header, When any Networking tool is invoked, Then the response is HTTP 401 and the body lists the required header name — the request never reaches DigitalOcean's API.
- **AC3**: Given a valid token, When `digitalocean_networking_list_vpcs` is called with no `vpc_id`, Then it returns a paginated list of VPCs with a `has_more` flag; When called with a specific `vpc_id`, Then it returns that VPC's full detail plus its member-resource count and its current peerings (merging `GET /v2/vpcs/{id}`, `GET /v2/vpcs/{id}/members`, and `GET /v2/vpcs/{id}/peerings` into one response) — and the tool is annotated `readOnlyHint: true`.
- **AC4**: Given a valid token and an incomplete payload (e.g. missing `name` or `region`), When `digitalocean_networking_create_vpc` is called, Then DigitalOcean's own validation error is surfaced as a structured `invalid_argument` error carrying DigitalOcean's message, not swallowed or turned into a generic failure.
- **AC5**: Given a valid token, an existing `vpc_id`, and only a `description` field, When `digitalocean_networking_update_vpc` is called, Then only the given field changes (DigitalOcean's `PATCH` partial-update semantics) and the tool's description states this explicitly, in contrast to the whole-object-replace tools below.
- **AC6**: Given a valid token and a `vpc_id` that still has member resources (Droplets, Load Balancers, etc. attached), When `digitalocean_networking_delete_vpc` is called, Then DigitalOcean's own precondition-failure response is surfaced as a structured error (not an HTTP 500, not silently retried) and the tool is annotated `destructiveHint: true`.
- **AC7**: Given a valid token, When `digitalocean_networking_manage_vpc_peering` is called with `action="create"` and fewer or more than exactly two `vpc_ids`, Then it returns a structured `invalid_argument` error without calling DigitalOcean; When called with exactly two valid `vpc_ids`, Then the peering is created. When called with `action="delete"`, Then it requires an explicit `vpc_peering_id` (no name lookup) and the tool is annotated `destructiveHint: true`.
- **AC8**: Given a valid token, When `digitalocean_networking_list_firewalls` is called with an existing `firewall_id`, Then it returns that firewall's full rule/droplet/tag detail; Given a `firewall_id` that does not exist (or belongs to another account), Then the response is a structured `not_found` error, not an HTTP 500.
- **AC9**: Given a valid token, an existing `firewall_id`, and a complete desired `inbound_rules`/`outbound_rules`/`droplet_ids`/`tags` payload, When `digitalocean_networking_update_firewall` is called, Then the firewall's rules/membership become exactly that payload (DigitalOcean's `PUT` whole-object-replace semantics) and the tool's description states that unspecified arrays are **not** preserved — the tool does not invent partial-merge behaviour DigitalOcean doesn't have.
- **AC10**: Given a valid token, When `digitalocean_networking_delete_firewall` is called, Then it requires an explicit single `firewall_id` argument (no name lookup, no "all firewalls"), is annotated `destructiveHint: true`, and its description states the action is irreversible.
- **AC11**: Given a valid token, When `digitalocean_networking_list_domains` is called with an existing `domain_name`, Then it returns that domain's detail (zone file, TTL); Given a valid token and a `domain_name` that already exists on the account, When `digitalocean_networking_create_domain` is called with that name, Then DigitalOcean's own conflict error is surfaced as a structured error, not a generic failure.
- **AC12**: Given a valid token and an existing `domain_name`, When `digitalocean_networking_manage_domain_record` is called with `action="create"`, `"update"`, or `"delete"`, Then each maps to DigitalOcean's record create/patch/delete endpoints respectively; `action="delete"` requires an explicit `domain_record_id` (no "delete all records matching type X") and the tool is annotated `destructiveHint: true`.
- **AC13**: Given a valid token, When `digitalocean_networking_list_load_balancers` is called with an existing `lb_id`, Then it returns that load balancer's full detail including `droplet_ids` and `forwarding_rules`; When `digitalocean_networking_update_load_balancer` is called with a complete desired state, Then the load balancer's droplets/forwarding-rules become exactly that payload (DigitalOcean's `PUT` whole-object-replace semantics, documented the same way as `update_firewall`, AC9).
- **AC14**: Given a valid token, When `digitalocean_networking_delete_load_balancer` is called, Then it requires an explicit single `lb_id` argument, is annotated `destructiveHint: true`, and its description states the action is irreversible and does not delete the Droplets behind it.
- **AC15**: Given two concurrent `tools/call` requests carrying two different tenants' `X-DigitalOcean-Api-Token` values, When both complete, Then neither response contains data retrieved using the other request's token — verified by a concurrency test asserting no shared mutable state keyed only by in-process globals.
- **AC16**: Given DigitalOcean's API returns `429` or a `5xx`, When a tool call is in flight, Then the connector retries with backoff honouring `Retry-After` up to the configured budget, and if the budget is exhausted, returns a structured `rate_limited` or `upstream_error` rather than hanging past the per-call timeout.
- **AC17**: Given the repository's `README.md`, Then it documents the single `X-DigitalOcean-Api-Token` header (purpose, how to obtain it, required scope), lists all 17 tools in its tool table, and its "MSPbots Connector" section is byte-for-byte identical to `~/.claude/skills/vendor-mcp-development/reference/readme-connector-section.md`.

## Tech design

### Conclusion

Build a new Python 3.12 + `uv` + FastMCP service module within `MSPbotsAIFramework/digitalocean-mcp` (third ticket to add code to this still-empty repo) implementing 17 MCP tools against DigitalOcean's public REST API, covering four resource groups: VPCs (incl. peering), Firewalls, Domains/DNS, and Load Balancers. One `httpx.AsyncClient` per request scoped via `contextvars`; credentials come from the single Header `X-DigitalOcean-Api-Token` (reused from PRD-21338's design, see § Decisions made by DEV01), forwarded as `Authorization: Bearer <token>` on every outbound call; nothing cached across requests.

### Where the current implementation lives

Nothing exists yet for Networking. The repository has one commit on `main` (34681e7): a two-line `README.md` — confirmed via `prepare_repo.py` and a direct read of the worktree. This is a from-scratch build (SOP "main line A"). Sibling branches `origin/dev/PRD-21338` and `origin/dev/PRD-21343` (neither merged) have designs for the Apps and Inference resource groups but no code either — there is no existing code in this repository to cite with `path:line` for Networking or otherwise. The closest shape references are: the SOP's own template structure (`~/.claude/skills/vendor-mcp-development/SKILL.md` §A3), and PRD-21338's/PRD-21343's design documents for the conventions this design reuses (credential header name, tool-naming scheme, assumed per-resource-group module layout).

### Option analysis

| Option | Approach | Pros | Cons | Verdict |
|---|---|---|---|---|
| Mirror all 19 networking-tagged groups / 97 raw operations 1:1 | One MCP tool per DigitalOcean operation | Simplest mapping, no judgement calls | Blows the SOP's ≤ 20 tools/service ceiling by ~5x on its own; floods `tools/list` with several enterprise/niche/unstable groups (BYOIP Prefixes, Partner Network Connect, Reserved IPv6, VPC NAT Gateways, VPC Routes/Subnets marked `[Public Preview]` in DigitalOcean's own spec) that are a poor fit for a first version | Rejected — violates SOP §2 |
| Cover every networking tag group at a reduced tool count each (capability-shaped, ~1-2 tools/group) | ~25-30 tools spanning all 19 groups | More "complete" coverage of the product name | Still roughly 1.5-2x this ticket's chosen size, worsening the already-flagged repo-wide ≤ 20 ceiling for comparatively low marginal value — Certificates/CDN/BYOIP/IPv6/NAT-Gateways/Preview-Routes-and-Subnets are not what "connect to my network", "secure my network", or "point my domain somewhere" ordinarily mean | Rejected |
| Four core resource groups only (chosen): VPCs + Peering, Firewalls, Domains/DNS, Load Balancers — capability-shaped, discrete sub-resource endpoints folded into whole-object updates where DigitalOcean's own `PUT` already covers them | 17 tools covering the operations an agent is most likely to be asked for: "put this behind a VPC", "open/close a firewall port", "point this domain at that IP", "add a Droplet behind this load balancer" | Cuts Certificates, Reserved/Floating IPs, CDN, BYOIP, Partner Network Connect, VPC NAT Gateways, `[Public Preview]` VPC Routes/Subnets, Regions from v1 | **Chosen** — additive later, no breaking change; keeps this ticket's contribution to the shared tool budget comparable to PRD-21338's (18), not roughly double it |

No framework alternative to FastMCP was considered in depth: the SOP mandates it for Python services and PRD-21338/PRD-21343 both already adopted it for this same repository, so matching it is "reuse the organization's existing pattern, already established in this repo's own sibling branches" (SOP A3; `templates-design.md` §3 selection order: reuse > open source > self-build).

### Data & API contract

**Credential header** (declared to the MCP gateway at registration time, SOP §3.1, identical to PRD-21338/PRD-21343 — DigitalOcean's account-level Personal Access Token works across App Platform, Serverless Inference, and the core networking REST API, so one shared header keeps the connector to one credential form):

| Header | Required | Type | Description |
|---|---|---|---|
| `X-DigitalOcean-Api-Token` | yes | password | DigitalOcean Personal Access Token (Control Panel → API → Tokens → Generate New Token). Needs read/write scope for the write tools; a read-only token works for the read-only tools and returns DigitalOcean's own 403 for write attempts. |

**Upstream base URL**: `https://api.digitalocean.com`. Auth: `Authorization: Bearer <token>` built from the Header above (DigitalOcean `securitySchemes.bearer_auth`, confirmed in the public OpenAPI spec, 2026-11-02).

**Tool → DigitalOcean operation mapping** (17 tools over 31 of the ~97 networking-tagged operations; `readOnlyHint`/`destructiveHint`/`idempotentHint` per SOP A4):

| Tool | Hints | Maps to DigitalOcean operation(s) |
|---|---|---|
| `digitalocean_networking_list_vpcs` | readOnly, idempotent | `GET /v2/vpcs` (`vpcs_list`); with `vpc_id`: `GET /v2/vpcs/{id}` (`vpcs_get`) + `GET /v2/vpcs/{id}/members` (`vpcs_list_members`) + `GET /v2/vpcs/{id}/peerings` (`vpcs_list_peerings`) |
| `digitalocean_networking_create_vpc` | — | `POST /v2/vpcs` (`vpcs_create`) |
| `digitalocean_networking_update_vpc` | idempotent | `PATCH /v2/vpcs/{id}` (`vpcs_patch`) |
| `digitalocean_networking_delete_vpc` | destructive | `DELETE /v2/vpcs/{id}` (`vpcs_delete`) |

**Deferred (not built in this ticket)** — 10 tag groups / ~66 operations: Certificates (`certificates_list/create/get/delete`, 4 ops — Load Balancers already reference a certificate by opaque `certificate_id`, so HTTPS termination works without a dedicated cert-management tool in v1); Reserved IPs + Actions and the legacy Floating IPs + Actions alias (8 ops combined — DigitalOcean renamed Floating→Reserved on 2026-06-16 per the spec's own tag description, functionally identical; deferred as a unit); Reserved IPv6 + Actions (5 ops, newer/narrower use case); CDN Endpoints (6 ops, a delivery/caching concern more than core networking); VPC NAT Gateways (5 ops, newer feature); VPC Routes `[Public Preview]` and VPC Subnets `[Public Preview]` (11 ops combined, not GA in DigitalOcean's own spec); BYOIP Prefixes (6 ops) and Partner Network Connect (9 ops, both enterprise bring-your-own-IP / dedicated-interconnect features, different risk/audience profile); Regions (1 op — all four built resource groups accept `region` as a plain string and DigitalOcean's own validation error already names an invalid region, so a dedicated lookup tool isn't load-bearing for v1, unlike Apps where `create_app`'s spec needed a closed region×instance-size list).

Also deferred: the discrete `firewalls_assign_droplets`/`firewalls_delete_droplets`/`firewalls_add_tags`/`firewalls_delete_tags` (4 ops) and `loadBalancers_add_droplets`/`loadBalancers_remove_droplets`/`loadBalancers_add_forwardingRules`/`loadBalancers_remove_forwardingRules`/`loadBalancers_delete_cache` (5 ops) sub-resource endpoints — `update_firewall`/`update_load_balancer`'s whole-object `PUT` already covers changing those arrays (see § Decisions made by DEV01); `loadBalancers_delete_cache` (Global Load Balancer CDN cache purge) specifically is deferred as a narrower, newer feature with no equivalent in the chosen tool set yet.

### Key flow / sequence

```
Agent (tenant) --tools/call(digitalocean_networking_update_firewall, Header: X-DigitalOcean-Api-Token)--> Gateway
  --HTTP, Header forwarded--> digitalocean-mcp /mcp
    middleware: read Header -> ContextVar; missing -> 401 (AC2)
    tool: digitalocean_networking_update_firewall(firewall_id, inbound_rules, outbound_rules, droplet_ids, tags)
      -> client.py builds Authorization: Bearer <token> from ContextVar
      -> PUT https://api.digitalocean.com/v2/firewalls/{firewall_id}  (whole-object replace, AC9)
      -> on 429/5xx: retry with backoff honouring Retry-After, budget-bounded (AC16)
      -> map DigitalOcean response/error onto the tool's return shape / error envelope
    middleware: ContextVar reset() in finally, regardless of success/failure
  <-- compact JSON result or {"error": {...}} --
<-- tools/call result --
```

### Non-functional

- **Idempotency & concurrency**: read tools (`list_*`) are naturally idempotent. `create_vpc`/`create_domain`/`create_load_balancer`/`manage_vpc_peering(action="create")`/`manage_domain_record(action="create")` are not idempotent — repeated calls create repeated resources; this is DigitalOcean's own semantics, documented in the tool description rather than papered over with client-side dedup (which would need persistent state, forbidden by the stateless requirement). `update_vpc` (PATCH, partial) and `update_firewall`/`update_load_balancer` (PUT, whole-replace) are idempotent: calling either again with the same payload produces the same end state.
- **Performance**: `list_vpcs`/`list_firewalls`/`list_domains`/`list_load_balancers` paginate when no specific id is given (default/hard-cap per SOP A4, same pattern as PRD-21338's `list_apps`); one `httpx.AsyncClient` per process, reused across requests within a process (connection pooling), never across tenants' *data* — only the transport is shared, credentials are per-request.
- **Security**: credentials never leave the request's lifetime — no logging of the token, no writing it to disk/env/cache; `gitleaks detect` run before delivery (SOP §11); destructive tools (`delete_vpc`, `delete_firewall`, `delete_domain`, `manage_vpc_peering(action="delete")`, `manage_domain_record(action="delete")`, `delete_load_balancer`) require an explicit resource id, never a name lookup or a "match all" filter, so there is no way to construct an accidental bulk-destructive call. Firewall rule payloads can carry CIDR ranges and port specs but no credentials — logs may include them for observability.
- **Multi-tenant isolation**: `contextvars.ContextVar` scopes the credential per request (set in middleware, `reset()` in `finally`); no module-level or global mutable state holds tenant data between requests (AC15); the `httpx.AsyncClient` instance itself carries no auth state — the `Authorization` header is attached per-outbound-call from the context var, not baked into client construction.
- **Observability**: structured logs include tool name, DigitalOcean operation, resource id when present (vpc/firewall/domain/lb/peering/record id), outcome, latency; explicitly never include the token header value. Firewall rule bodies and DNS record values are not secrets and may appear in logs at debug level, consistent with their visibility in the DigitalOcean control panel itself.

### Rollout & rollback

No feature flag — this is new tooling in a connector that doesn't fully exist until registered/updated. Rollout is the SOP's standard path: merge to `main` → `uv run pytest` on the merged code → `/api/deploy-int` (or `/api/vendor-register` if this is the first ticket among the three siblings to land) → INT health check → connector wiki page. ### Test strategy

- **Unit** (`tests/networking/test_tools.py`): `tools/list` snapshot assertion (17 tools, names, hint flags, description length limits — AC1); per-tool argument validation (e.g. `manage_vpc_peering` requires exactly 2 `vpc_ids` on create, AC7); DigitalOcean error-response → envelope mapping for each error code using mocked `httpx` responses, no real DigitalOcean account needed.
- **Unit** (`tests/networking/test_client.py`): retry/backoff on 429 and 5xx honouring `Retry-After`, bounded retry budget (SOP §5: single call < 120s including retries).
- **Shared** (`tests/test_middleware.py`): missing-Header → 401 (AC2); concurrency isolation (AC15).
- **Integration, local, placeholder credentials** (SOP A5): `initialize → tools/list → tools/call` against a running local instance with a syntactically plausible but fake token, asserting tool count and names/params are correct and that calls fail with DigitalOcean's real 401 (proving the Header → `Authorization` wiring works end-to-end) rather than a connector-side error.
- **Needs a real DigitalOcean account** (listed in the Self-test report as "needs a real vendor account," not blocking per `mcp-track.md` §3 "Completion criteria"): the exact precondition-failure shape for deleting a VPC with members (AC6); a real VPC-peering lifecycle (AC7); real firewall/load-balancer whole-object-replace behaviour against an account with existing Droplets (AC9/AC13).

Once PRD-21338/PRD-21343/PRD-21344 land, the shared `middleware.py`/`settings.py`/`server.py` become a regression surface for all resource groups together — whichever dev leg lands second (or later, including this one) needs to re-run the shared middleware tests, not just its own group's tests (same note PRD-21343 recorded).

### Risks & dependencies

- **Risk**: DigitalOcean API rate limits (exact thresholds undocumented in the public reference, same risk PRD-21338 flagged) could make `list_vpcs`/`list_firewalls`/`list_domains`/`list_load_balancers` calls for tenants with many resources slow or throttled. Mitigation: pagination with sane defaults, backoff honouring `Retry-After` (AC16), surfaced as `rate_limited` rather than hanging.
- **Risk**: whole-object `PUT` on Firewalls and Load Balancers (chosen in § Decisions made by DEV01 to avoid building separate add/remove tools) means an agent that fetches a firewall, adds one rule, and calls `update_firewall` with only that new rule (forgetting to include the existing rules) will **replace** the firewall's rules rather than append — this is DigitalOcean's own semantics, not a bug, but it is a real misuse mode. Mitigation: the tool description explicitly states the whole-object-replace behaviour (AC9/AC13) and recommends reading `list_firewalls`/`list_load_balancers` with the resource id first to get the current full state before calling update.
- **Risk**: four tickets share one repository and one `dev-lock`. Mitigation: this ticket's dev leg takes the lock only for the duration of its own change, touches only the `networking/` tool module and the shared scaffolding (`server.py`, `client.py` base pattern, `errors.py`, `middleware.py`, `settings.py`) — which the sibling tickets also need and should extend, not duplicate. PRD-21338 and PRD-21343 are also still at the design stage (not yet in development) at the time of this design, so there is no concurrent-edit conflict today; whichever dev leg starts first effectively decides the shared scaffolding's exact shape, and the others should follow suit rather than re-litigate it (same note PRD-21343 recorded for its own module-layout assumption).
- **Risk / flagged cross-ticket decision**: the shared repo's aggregate tool count (18 + 4 + 17 = 39 before PRD-21344/Kubernetes contributes anything) is well past the SOP's ≤ 20-per-service ceiling. This ticket cannot resolve that alone; recorded in Product design § Open questions and here so the review leg sees it explicitly rather than discovering it at merge time (same flag PRD-21343 raised, now with a higher running total).
- **Dependency**: none on another ClickUp ticket. Depends on DigitalOcean's public API remaining as documented (external, unversioned dependency common to all vendor MCP connectors — not specific to this design).

## Decisions made by DEV01

No one was available to ask (unattended design leg), so the following first-version choices were made and are flagged here for product/engineering to revisit if wrong — changing any of them is a comment + move back to `5b - ready for groom`, not a silent edit:

- **Scope: 4 of DigitalOcean's 19 networking-tagged groups (VPCs+peering, Firewalls, Domains/DNS, Load Balancers), not all 19** — these four cover the overwhelming majority of real "configure my DigitalOcean network" requests (put something on a private network, open/close ports, point a domain somewhere, load-balance traffic); the ticket itself names no specific capability, so this design scoped to the highest-value, most stable (none are `[Public Preview]`, none are enterprise-only) subset. Alternative considered: cover every tagged group now — rejected, see Option analysis (roughly doubles this ticket's size for comparatively low marginal value and worsens the already-flagged repo-wide tool-count ceiling).
- **Deferred: Certificates, Reserved IPs/Floating IPs (+Actions), Reserved IPv6 (+Actions), CDN Endpoints, VPC NAT Gateways, VPC Routes/Subnets `[Public Preview]`, BYOIP Prefixes, Partner Network Connect, Regions** — each individually judged out of a first version's core scope (see § Option analysis and § Data & API contract "Deferred" for the specific reason per group: delivery/caching concern, legacy/rename pair, not-GA, enterprise-only, or not load-bearing given the other four groups' own validation). Alternative considered for each: build it now — rejected per-group with the reasons listed; all are additive follow-ups.
- **Cut discrete add/remove droplet/tag/forwarding-rule sub-endpoints for Firewalls and Load Balancers, rely on the whole-object `PUT` update tool** — DigitalOcean's own `PUT` for both resources already replaces the full rule/membership arrays, so a dedicated `update_firewall`/`update_load_balancer` tool reaches the same end state as the discrete add/remove endpoints without adding 9 more tools; this mirrors PRD-21338's identical choice for `update_app` (PUT replace semantics, no client-side merge). Alternative considered: expose each discrete endpoint as its own tool — rejected as pure tool-count inflation for functionality already reachable.
- **Credential header `X-DigitalOcean-Api-Token`, reused verbatim from PRD-21338/PRD-21343** — DigitalOcean's account-level Personal Access Token authenticates the core networking REST API the same way it authenticates App Platform and Serverless Inference; since all four resource-group tickets share one repository and (per the org admin's framing) one connector registration, one credential header keeps the connector to one credential form instead of fragmenting into multiple tokens for what is, in DigitalOcean's own account model, a single account. Alternative considered: a dedicated `X-DigitalOcean-Networking-Token` header — rejected for the same reason PRD-21343 rejected a dedicated Inference header.
- **Tool naming `digitalocean_networking_<verb>_<resource>`, reused verbatim from PRD-21338's scheme** — the `networking` segment disambiguates from the `apps`/`inference` segments already chosen by sibling tickets, and from whatever PRD-21344 (Kubernetes) will choose, avoiding name collisions across the shared `tools/list` (e.g. a future Kubernetes `list_load_balancers`-equivalent for Kubernetes-managed load balancers would collide with this ticket's `digitalocean_networking_list_load_balancers` without the group segment). Alternative considered: flat `digitalocean_<verb>_<resource>` — rejected for the same collision reason PRD-21338/PRD-21343 already rejected it.
- **VPC updates via `PATCH` (partial) vs. Firewall/Load-Balancer updates via `PUT` (whole-replace)** — not a style inconsistency: this follows each resource's own documented primary update verb in DigitalOcean's API. VPCs only have 2-3 simple top-level fields (`name`, `description`, `default`) and DigitalOcean's `PATCH` is the documented partial-update path for them; Firewalls and Load Balancers have no `PATCH` endpoint at all — `PUT` (whole-object replace, including the rule/membership arrays) is their only update path. Alternative considered: use `PUT` for VPCs too for "consistency" — rejected because it would silently require re-submitting `name`+`description`+`default` on every VPC update even when only one field changes, which is worse ergonomics for no real benefit.
- **Domain records updated via `PATCH`, not `PUT`** — DigitalOcean's API documents both verbs for a domain record; `PATCH` is chosen so `manage_domain_record(action="update")` can change a single field (e.g. just the TTL) without resubmitting the full record body, consistent with the tool being a single action-based lifecycle tool rather than one tool per record field combination.
- **Module layout: assumed `src/digitalocean_mcp/networking/` subpackage** (`client.py`, `vpcs.py`, `firewalls.py`, `dns.py`, `load_balancers.py`) — mirrors PRD-21343's own assumed `inference/` subpackage layout for the same repository; no code exists yet from any sibling ticket to confirm this against. Alternative considered: flat `src/digitalocean_mcp/` with per-group filename prefixes — not chosen, for the same reason PRD-21343 didn't choose it; whichever dev leg lands first effectively decides this, and later tickets should follow suit.

To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.
