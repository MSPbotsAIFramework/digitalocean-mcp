## Requirement understanding

One line: Connect DigitalOcean App Platform ("Apps") as a new MCP connector so Claude, ChatGPT, Cursor, or any MCP-compatible AI client can manage DigitalOcean apps and their deployments through the MSPbots Agent Platform, with credentials encrypted per tenant and every action logged.

Connect it to give Claude, ChatGPT, Cursor, or any MCP-compatible AI live access, with credentials encrypted and every action logged. Link: https://conduit.wyre.ai/plugins/digitalocean-apps". Three sibling tickets cover the other DigitalOcean resource groups in the same shared repository: PRD-21343 (Inference Model Catalog), PRD-21344 (Kubernetes/DOKS), PRD-21345 (Networking) — all still in `5b - ready for groom` at the time of this design. "Credentials encrypted" and "every action logged" are platform-level properties the Agent Platform already provides for every connector (per-tenant encrypted credential storage, Header-scoped delivery, gateway-side audit log) — see `wiki: ProductDocs/15-Capabilities.md § Connectors section (_verified_ 2026-08-28, v4.1.517)`. ## Product design

### Goals / Non-goals

**Goals**
- Give an Agent Platform tenant, once connected, the ability to inspect and operate DigitalOcean App Platform apps through MCP tools: list/inspect apps, create/update/delete an app, restart it, validate an app spec, manage deployments (list/inspect/trigger/cancel), read logs, inspect instances, roll back a bad deployment, see events and alerts, and look up the regions/instance sizes needed to build an app spec.
- Every write/destructive tool call must act only on an explicitly supplied app/deployment id — no name-based matching, no "do this to all my apps" bulk tools.
- Standard MSPbots connector experience: shows up in the Library with a credential (API token) connect form, `tools/list` enumerates the tools with one-line descriptions, each tool call is scoped to the tenant whose Header carried the token.

**Non-goals (this ticket)**
- The other three DigitalOcean resource groups (Inference Model Catalog — PRD-21343, Kubernetes/DOKS — PRD-21344, Networking — PRD-21345). They live in the same repository but are designed and delivered on their own tickets.
- Any DigitalOcean resource outside App Platform (Droplets, Spaces, Databases, Load Balancers, etc.) that isn't one of the three sibling tickets either — out of scope entirely unless a future ticket asks for it.
- Remote shell / exec access into a running app component (`apps_get_exec*`), scheduled "Jobs" component invocations (`apps_*_job_invocations*`), bandwidth metrics, and alert-destination configuration — deliberately deferred; see Tech design § Reuse & cleanup and § Risks for why.
- OAuth-based auth — DigitalOcean App Platform uses a single bearer token, so there is no authorization-code flow to support.
- A UI. This is a backend MCP connector; the only user-facing surface is the Agent Platform's existing generic connector chrome (Library card, connect form, tool list), which this ticket does not change.

### Acceptance criteria AC1..AC15

- **AC1**: Given the connector is running and a client sends `tools/list`, Then the response includes all 18 `digitalocean_apps_*` tools (see Tech design § Change list for the full list), each with a description whose first line is ≤ 100 characters and whose full text is ≤ 500 characters, and each annotated with the correct `readOnlyHint`/`destructiveHint`/`idempotentHint` for its operation.
- **AC2**: Given a `tools/call` request that is missing the `X-DigitalOcean-Api-Token` header, When the tool is invoked, Then the response is HTTP 401 and the body lists the required header name — the request never reaches DigitalOcean's API.
- **AC3**: Given a valid token, When `digitalocean_apps_list_apps` is called with no arguments, Then it returns at most 50 apps (default) with a `has_more` flag; When called with `limit=200`, Then it returns at most 200 (the hard cap) even if more exist upstream.
- **AC4**: Given a valid token and an existing app id, When `digitalocean_apps_get_app` is called, Then it returns that app's current spec and active deployment id; Given an app id that does not exist (or belongs to another account), When called, Then the response is a structured `not_found` error, not an HTTP 500 and not a stack trace.
- **AC5**: Given a valid token and an app spec, When `digitalocean_apps_create_app` is called, Then DigitalOcean's own spec validation errors are surfaced as a structured `invalid_argument` error with DigitalOcean's message, not swallowed or turned into a generic failure.
- **AC6**: Given a valid token, an existing app id, and an updated spec, When `digitalocean_apps_update_app` is called, Then the app is updated and the tool documents (in its description) that unspecified spec fields follow DigitalOcean's own PUT replace-semantics — the tool does not invent partial-merge behaviour DigitalOcean doesn't have.
- **AC7**: Given a valid token, When `digitalocean_apps_delete_app` is called, Then it requires an explicit single app id argument (no name lookup, no "all apps"), is annotated `destructiveHint: true`, and its description states the action is irreversible.
- **AC8**: Given a valid token and an app id, When `digitalocean_apps_restart_app` is called with no `component_names`, Then all components restart; When called with a list of component names, Then only those components restart; the tool is annotated `destructiveHint: true`.
- **AC9**: Given a valid token and an app with a deployment already in progress, When `digitalocean_apps_create_deployment` is called again, Then DigitalOcean's conflict response is surfaced as a structured `upstream_error` (not retried as if it were a transient failure, not silently discarded).
- **AC10**: Given a valid token and an app id, When `digitalocean_apps_get_logs` is called with no `deployment_id`, Then it defaults to the active deployment; with no `component_name`, Then it returns the aggregate log across components; Given an unsupported `log_type` value, Then it returns a structured `invalid_argument` error.
- **AC11**: Given a valid token and an app id, When `digitalocean_apps_manage_rollback` is called with `action="commit"` or `action="revert"`, Then the tool is annotated `destructiveHint: true` and requires the explicit `deployment_id` that was returned by a prior `action="start"` call — it does not guess which deployment to roll back to.
- **AC12**: Given a valid token, When `digitalocean_apps_get_deployment_options` or `digitalocean_apps_validate_spec` is called, Then neither requires an app id (they are account-level/stateless reference operations) and both are annotated `readOnlyHint: true`.
- **AC13**: Given two concurrent `tools/call` requests carrying two different tenants' `X-DigitalOcean-Api-Token` values, When both complete, Then neither response contains data retrieved using the other request's token — verified by a concurrency test asserting no shared mutable state keyed only by in-process globals.
- **AC14**: Given DigitalOcean's API returns `429` or a `5xx`, When a tool call is in flight, Then the connector retries with backoff honouring `Retry-After` up to the configured budget, and if the budget is exhausted, returns a structured `rate_limited` or `upstream_error` rather than hanging past the per-call timeout.
- **AC15**: Given the repository's `README.md`, Then it documents the single `X-DigitalOcean-Api-Token` header (purpose, how to obtain it, required scope), and its "MSPbots Connector" section is byte-for-byte identical to `~/.claude/skills/vendor-mcp-development/reference/readme-connector-section.md`.

### Open questions

- [not blocking] DigitalOcean API tokens can be scoped read-only or read-write at creation time (DigitalOcean account setting, not something this connector controls). If a tenant connects a read-only token, every write/destructive tool will fail with DigitalOcean's own 403, surfaced as a structured `unauthorized`/`upstream_error` — this design does not add a client-side "read-only mode" toggle; DigitalOcean's token scope is the single source of truth. If product wants a softer UX (e.g. hiding write tools for read-only tokens), that is a follow-up, not blocking this first version.
- [assumed] The ticket's Conduit link (`https://conduit.wyre.ai/plugins/digitalocean-apps`) is a third-party reference only, not a spec to match tool-for-tool — per `mcp-track.md` 2.1, Conduit/third-party links are reference material, not a requirement source, and per the SOP, third-party MCP implementations are never ported or mirrored. This design is built clean-room from DigitalOcean's own public API reference. If product specifically wants parity with the Conduit plug-in's exact tool set, that would need to be stated explicitly and would be a requirement change (S0c-style), not something this design can infer from a marketing link.
- [assumed] "Jobs" component invocations, exec/shell access, bandwidth metrics, and alert-destination writes are assumed out of scope for v1 because the ticket's stated need is "manage apps and deployments," not full App Platform observability/ops tooling. See Tech design § Reuse & cleanup for the full list and rationale. If any of these turn out to matter, they are additive (new tools, no breaking change) and can be picked up as a follow-up ticket.

## Tech design

### Conclusion

Build a new Python 3.12 + `uv` + FastMCP service in `MSPbotsAIFramework/digitalocean-mcp` (first commit to this empty repo for the Apps resource group), following the vendor-mcp-development SOP structure: `POST /mcp` (Streamable HTTP, stateless) + `GET /health`, one `httpx.AsyncClient` per request scoped via `contextvars`, a thin DigitalOcean API client wrapping `https://api.digitalocean.com/v2/apps*`, and 18 MCP tools that group DigitalOcean's 38 raw Apps-tag endpoints into agent-facing capabilities (not a 1:1 endpoint mirror). Credentials come from a single Header, `X-DigitalOcean-Api-Token`, mapped to `Authorization: Bearer <token>` on every outbound call; nothing is cached across requests.

### Where the current implementation lives

Nothing exists yet. The repository has one commit: `README.md` (2 lines) at `main` (34681e7) — confirmed via `prepare_repo.py` and a direct read of the worktree. This is a from-scratch build (SOP "main line A"), not a modification of existing code. There is no adjacent DigitalOcean implementation in MSPbotsAIFramework to pattern-match against (searched: no other repo named `digitalocean*` or `do-*mcp` in the org at the time this design's sibling tickets were triaged — see the earlier `[BLOCKED · vendor-mcp]` comment, 2026-10-30, which ran the full 129-repo listing). The closest shape reference is the SOP's own template structure (`SKILL.md` A3) and other delivered MCP connectors' documented conventions (error envelope, Header naming, tool naming) — there is no code to cite with `path:line` because none exists.

### Option analysis

| Option | Approach | Pros | Cons | Verdict |
|---|---|---|---|---|
| Mirror DigitalOcean's 38 endpoints 1:1 as 38 tools | One MCP tool per API operation | Simplest mapping, no judgement calls | Exceeds the SOP's ≤ 20 tools/service ceiling by ~2x; floods `tools/list` with near-duplicate log/rollback/exec variants that differ only in which id is implicit; worse token economy for the calling agent | Rejected — violates SOP §2 |
| Group into capability-shaped tools (chosen) | 18 tools; merge the 4 log-retrieval endpoints into one parameterized tool, the 4 rollback-lifecycle endpoints into one action-based tool, the 2 event endpoints into one, the 2 regions/instance-size lookups into one | Fits the ≤ 20 ceiling with headroom for future fixes; each tool maps to one agent-recognizable action ("get logs", "manage rollback"); fewer, clearer tool descriptions | Each merged tool has a slightly larger parameter surface (e.g. `get_logs` takes optional `deployment_id`/`component_name`/`log_type`) — documented per-tool, not hidden | **Chosen** |
| Defer non-core sub-resources (exec, job invocations, bandwidth metrics, alert destinations) to a follow-up | Ship 18 tools covering app/deployment/log/rollback/event/alert/reference-data operations now; leave exec, scheduled jobs, metrics, and alert-destination writes for later | Keeps v1 scoped to the ticket's literal ask ("manage apps and deployments"); exec access in particular is security-sensitive (remote shell into a tenant's running container) and deserves its own review, not a drive-by inclusion | Four DigitalOcean capabilities aren't reachable from day one | **Chosen** — additive later, no breaking change if added |

No framework alternative to FastMCP was considered in depth: the SOP mandates it for Python services (`stateless_http=True`, request isolation via `contextvars`) and every other MSPbots vendor MCP service in MSPbotsAIFramework uses the same stack, so matching it is "reuse the organization's existing pattern," not a from-scratch choice (SOP A3; `templates-design.md` §3 selection order: reuse > open source > self-build — FastMCP + httpx + pydantic are the already-adopted open-source stack here, nothing to self-build at the HTTP/protocol layer).

### Reuse & cleanup

- **Reuse**: FastMCP (`stateless_http=True`) for the protocol layer and request lifecycle — not hand-rolling Streamable HTTP; `httpx.AsyncClient` for outbound calls with its built-in connection pooling — not a custom HTTP client; `pydantic`/`pydantic-settings` for request/response and settings validation. All three are the stack every other MSPbots vendor MCP repo already uses (per SOP A3), so this is adopting the organization's existing pattern, not introducing a new one.
- **New dependencies**: `fastmcp` (MCP protocol + stateless HTTP transport — this is the vendor-mandated framework, no alternative considered, see Option analysis), `httpx` (async HTTP client with timeout/retry support — replaces writing a raw `aiohttp`/`requests` wrapper), `pydantic` + `pydantic-settings` (schema validation — replaces hand-written dict validation). No DigitalOcean-specific SDK is used: DigitalOcean's official Python SDK (`pydo`) is synchronous and would fight FastMCP's async model and the SOP's per-request isolation requirement, so the thin async `httpx` wrapper in `client.py` is the correct amount of self-build here (there is no suitable existing async client to reuse, and `pydo` is not a fit — not "reuse" in name only).
- **Interfaces**: all 18 tool functions take explicit keyword arguments (no positional id soup) and return a single compact JSON string per the SOP's return-shape rules (`ensure_ascii=False`, no `indent=2`, `limit`/`has_more` for every `list_*` tool). This is the first version of every signature in this repo — there is nothing pre-existing to keep compatible with yet (SOP A1 "replacing an existing MCP" compatibility rule does not apply).
- **In-scope cleanup**: none — empty repository, nothing to clean up yet.
- **Suggested follow-ups** (out of this ticket, listed for product/future tickets, not acted on here): add `digitalocean_apps_get_exec_url` style remote-shell tooling behind its own security review; add scheduled-Jobs invocation tools (`apps_list_job_invocations` family) if a ticket needs them; add bandwidth-metrics tools if observability needs surface; add alert-destination write tooling if alert routing becomes a requirement. None of these are "unused code to delete" — they are DigitalOcean capabilities this first version deliberately does not expose.

### Data & API contract

**Credential header** (declared to the MCP gateway at registration time, SOP §3.1):

| Header | Required | Type | Description |
|---|---|---|---|
| `X-DigitalOcean-Api-Token` | yes | password | DigitalOcean Personal Access Token (Control Panel → API → Tokens → Generate New Token). Needs read/write scope for the write tools (AC listed above); a read-only token works for the read-only tools and returns DigitalOcean's own 403 for write attempts. |

**Upstream base URL**: `https://api.digitalocean.com`. Auth: `Authorization: Bearer <token>` built from the Header above (DigitalOcean `securitySchemes.bearer_auth`, confirmed in the public OpenAPI spec, 2026-11-02).

**Tool → DigitalOcean operation mapping** (18 tools over 27 of the 38 `/v2/apps*` operations; `readOnlyHint`/`destructiveHint`/`idempotentHint` per SOP A4):

| Tool | Hints | Maps to DigitalOcean operation(s) |
|---|---|---|
| `digitalocean_apps_list_apps` | readOnly | `GET /v2/apps` (`apps_list`) |
| `digitalocean_apps_get_app` | readOnly | `GET /v2/apps/{id}` (`apps_get`) |
| `digitalocean_apps_create_app` | — | `POST /v2/apps` (`apps_create`) |
| `digitalocean_apps_update_app` | idempotent | `PUT /v2/apps/{id}` (`apps_update`) |
| `digitalocean_apps_delete_app` | destructive | `DELETE /v2/apps/{id}` (`apps_delete`) |
| `digitalocean_apps_restart_app` | destructive | `POST /v2/apps/{app_id}/restart` (`apps_restart`) |
| `digitalocean_apps_validate_spec` | readOnly, idempotent | `POST /v2/apps/propose` (`apps_validate_appSpec`) |
| `digitalocean_apps_list_deployments` | readOnly | `GET /v2/apps/{app_id}/deployments` (`apps_list_deployments`) |
| `digitalocean_apps_get_deployment` | readOnly | `GET /v2/apps/{app_id}/deployments/{deployment_id}` (`apps_get_deployment`) |

**Deferred (not built in this ticket)** — 11 operations: `apps_get_exec`, `apps_get_exec_active_deployment` (remote shell access — security-sensitive, needs its own review); `apps_list_job_invocations`, `apps_get_job_invocation`, `apps_cancel_job_invocation`, `apps_get_job_invocation_logs` (scheduled "Jobs" component sub-feature, niche); `apps_get_metrics_bandwidth_daily`, `apps_list_metrics_bandwidth_daily` (observability metrics, not "manage apps and deployments"); `apps_assign_alertDestinations` (alert-routing configuration write); `apps_cancel_event`, `apps_get_event_logs` (granular build/control-plane event ops beyond listing).

**Error envelope** (every tool, per SOP §4): `{"error": {"code": "<not_configured|unauthorized|not_found|invalid_argument|rate_limited|upstream_error>", "message": "<human-readable>", "retryable": <bool>}}`. Tools never raise; empty results return an empty list/collection, never `not_found`.

Once registered on INT, every subsequent change to these 18 tool signatures is a breaking-change decision under SOP §13 (B3).

### Key flow / sequence

```
Agent (tenant) --tools/call(digitalocean_apps_get_logs, Header: X-DigitalOcean-Api-Token)--> Gateway
  --HTTP, Header forwarded--> digitalocean-mcp /mcp
    middleware: read Header -> ContextVar; missing -> 401 (AC2)
    tool: digitalocean_apps_get_logs(app_id, deployment_id?, component_name?, log_type?)
      -> client.py builds Authorization: Bearer <token> from ContextVar
      -> GET https://api.digitalocean.com/v2/apps/{app_id}/logs (or the more specific variant
         once deployment_id/component_name are given)
      -> on 429/5xx: retry with backoff honouring Retry-After, budget-bounded (AC14)
      -> map DigitalOcean response/error onto the tool's return shape / error envelope
    middleware: ContextVar reset() in finally, regardless of success/failure
  <-- compact JSON result or {"error": {...}} --
<-- tools/call result --
```

### Non-functional

- **Idempotency & concurrency**: read tools (`list_*`/`get_*`) are naturally idempotent. `create_app`/`create_deployment` are not idempotent — repeated calls create repeated resources; this is DigitalOcean's own semantics and is documented in the tool description rather than papered over with client-side dedup (which would need persistent state, forbidden by the stateless requirement). Rollback's `commit`/`revert` are one-shot and require the caller to hold the `deployment_id` from a prior `start`, so a retried `commit` either succeeds once or gets DigitalOcean's own "nothing to commit" error — not silently re-applied.
- **Performance**: `list_apps` paginates (default ≤ 50, hard cap ≤ 200, per SOP A4); logs/instances responses are size-bounded at 20000 characters with truncation + `has_more` per SOP A4; one `httpx.AsyncClient` per process, reused across requests within a process (connection pooling), never across tenants' *data* — only the transport is shared, credentials are per-request.
- **Security**: credentials never leave the request's lifetime — no logging of the token, no writing it to disk/env/cache; `gitleaks detect` run before delivery (SOP §11); destructive tools (`delete_app`, `restart_app`, rollback `commit`/`revert`, `cancel_deployment`) require an explicit resource id, never a name lookup or a "match all" filter, so there is no way to construct an accidental bulk-destructive call.
- **Multi-tenant isolation**: `contextvars.ContextVar` scopes the credential per request (set in middleware, `reset()` in `finally`); no module-level or global mutable state holds tenant data between requests (AC13); the `httpx.AsyncClient` instance itself carries no auth state — the `Authorization` header is attached per-outbound-call from the context var, not baked into client construction.
- **Observability**: structured logs include ticket-relevant fields (tool name, DigitalOcean operation, app/deployment id when present, outcome, latency) and explicitly never include the token header value or full response bodies that might carry tenant secrets (app spec can contain env vars marked `SECRET`).

### Rollout & rollback

No feature flag — this is a new connector; it doesn't exist until registered. Rollout is the SOP's standard "new vendor first registration" path: merge to `main` → `uv run pytest` on the merged code → `/api/vendor-register` (first time; subsequent changes use `/api/deploy-int`) → INT health check → connector wiki page. If registration or deploy fails, nothing is live yet, so there is nothing to roll back — fix forward and re-register/re-publish. Once live, a bad subsequent change is rolled back by reverting the offending commit on `main` and re-running `/api/deploy-int`; DigitalOcean-side application rollback (for a tenant's own app) is exactly what `digitalocean_apps_manage_rollback` exposes to the agent — that is a product feature of this connector, not an operational rollback mechanism for the connector itself.

### Risks & dependencies

- **Risk**: DigitalOcean API rate limits (exact thresholds undocumented in the public reference) could make `list_apps`/`list_deployments` calls for tenants with many apps slow or throttled. Mitigation: pagination with sane defaults (AC3), backoff honouring `Retry-After` (AC14), surfaced as `rate_limited` rather than hanging.
- **Risk**: App specs can embed `SECRET`-type environment variables (DigitalOcean's own app-spec concept). Mitigation: tools never log full spec/response bodies; only structured, secret-free fields (ids, names, phases) are logged.
- **Risk**: Four tickets share one repository and one `dev-lock`. Mitigation: this ticket's dev leg takes the lock only for the duration of its own change, touches only the `apps.py`/`deployments.py`/`observability.py`/`reference.py` tool modules and the shared scaffolding (`server.py`, `client.py`, `errors.py`, `middleware.py`, `settings.py`) — which the sibling tickets will also need and should extend, not duplicate. The sibling tickets (PRD-21343/21344/21345) are not yet in development (still `5b`), so there is no concurrent-edit conflict today; if one starts first, the second one through should rebase onto the shared scaffolding rather than recreate it.
- **Dependency**: none on another ClickUp ticket. Depends on DigitalOcean's public API remaining as documented (external, unversioned dependency common to all vendor MCP connectors — not specific to this design).

## Decisions made by DEV01

No one was available to ask (unattended design tick), so the following first-version choices were made and are flagged here for product/engineering to revisit if wrong — changing any of them is a comment + move back to `5b - ready for groom`, not a silent edit:

- **Tool count and grouping (18 tools, not 38 or 20+)** — chose capability-shaped tools over a 1:1 endpoint mirror to stay well under the SOP's ≤ 20 ceiling while leaving room for a small number of fixes later; alternative considered: mirror all 38 endpoints — rejected, see Option analysis.
- **Deferred capabilities: exec/shell access, scheduled Jobs invocations, bandwidth metrics, alert-destination writes** — excluded from v1 because the ticket's literal ask is "manage apps and deployments," and exec access in particular is security-sensitive enough to deserve its own review rather than a drive-by inclusion; alternative considered: include everything now — rejected to keep the first version's attack surface and review scope proportional to the stated need.
- **Credential header name `X-DigitalOcean-Api-Token`** — follows the SOP's `X-<Vendor>-<Credential>` convention and DigitalOcean's own terminology ("API token," not "API key"); alternative considered: `X-DigitalOcean-Token` (shorter) — rejected in favor of matching DigitalOcean's own naming so the README's "how to obtain it" instructions read naturally.
- **Tool naming `digitalocean_apps_<verb>_<resource>` (not just `digitalocean_<verb>_<resource>`)** — the `apps` segment is included because this repository will grow sibling tool groups for Inference/Kubernetes/Networking (PRD-21343/21344/21345) under the same `digitalocean_` vendor prefix; without the resource-group segment, names would collide or become ambiguous across those tickets (e.g. a future `digitalocean_list_regions` for Kubernetes droplets vs. this ticket's App Platform regions). Alternative considered: flat `digitalocean_<verb>_<resource>` — rejected because it doesn't scale to the four-resource-group repository structure that already exists.
- **`PUT`-replace semantics surfaced as-is on `update_app`, no client-side merge** — DigitalOcean's `PUT /v2/apps/{id}` already is whole-spec-replace; adding a client-side partial-merge would be inventing behaviour DigitalOcean doesn't have and would surprise callers who read DigitalOcean's own docs. Alternative considered: fetch-merge-then-put convenience behaviour — rejected as scope creep with a forgotten-field-wipe foot-gun.
