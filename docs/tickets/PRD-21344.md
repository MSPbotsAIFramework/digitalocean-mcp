## Requirement understanding

One line: Connect DigitalOcean Kubernetes (DOKS) as a new MCP connector so Claude, ChatGPT, Cursor, or any MCP-compatible AI client can manage DigitalOcean Kubernetes clusters and their node pools through the MSPbots Agent Platform, with credentials encrypted per tenant and every action logged.

The ticket is a short Conduit plug-in blurb (not a detailed spec), identical in shape to its three sibling tickets: "DigitalOcean Kubernetes (DOKS) is a Conduit plug-in. Connect it to give Claude, ChatGPT, Cursor, or any MCP-compatible AI live access, with credentials encrypted and every action logged. Link: https://conduit.wyre.ai/plugins/digitalocean-doks". Three sibling tickets cover the other DigitalOcean resource groups in the same shared repository: PRD-21338 (Apps — designed, `dev/PRD-21338`), PRD-21343 (Inference Model Catalog — designed, `dev/PRD-21343`), PRD-21345 (Networking — not yet designed at the time of this design). This ticket's scope is the Kubernetes Service (DOKS) tag only — cluster and node-pool lifecycle; the other resource groups are out of scope here and are designed on their own tickets.

"Credentials encrypted" and "every action logged" are platform-level properties the Agent Platform already provides for every connector (per-tenant encrypted credential storage, Header-scoped delivery, gateway-side audit log) — see `wiki: ProductDocs/15-Capabilities.md § Connectors section (_verified_ 2026-08-28, v4.1.517)`. They are not something this connector implements itself; the connector's job is to expose DOKS capabilities as MCP tools and read credentials only from request Headers (SOP §3.1).

## Product design

### Goals / Non-goals

**Goals**
- Give an Agent Platform tenant, once connected, the ability to inspect and operate DigitalOcean Kubernetes clusters and their node pools through MCP tools: list/inspect clusters, create/update/delete a cluster (with explicit control over how much gets destroyed), discover and apply control-plane upgrades, retrieve connection credentials (kubeconfig and token-based credentials), and manage node pools and individual nodes (list/inspect/create/update/delete, replace a single node).
- Every write/destructive tool call must act only on an explicitly supplied cluster/node-pool/node id — no name-based matching, no "do this to all my clusters" bulk tools, and no implicit "most destructive" default on the cluster-delete tool.
- Standard MSPbots connector experience: shows up in the Library with a credential (API token) connect form, `tools/list` enumerates the tools with one-line descriptions, each tool call is scoped to the tenant whose Header carried the token.
- Reuse what the sibling resource groups already decided rather than re-deciding it per ticket: the same credential Header, the same tool-naming scheme, the same shared scaffolding files.

**Non-goals (this ticket)**
- The other three DigitalOcean resource groups (Apps — PRD-21338, Inference Model Catalog — PRD-21343, Networking — PRD-21345). They live in the same repository but are designed and delivered on their own tickets.
- Any DigitalOcean resource outside the Kubernetes Service tag (Droplets, Spaces, Databases, Load Balancers as their own resource, etc.) that isn't one of the three sibling tickets either — out of scope entirely unless a future ticket asks for it.
- Container-registry integration (attach/detach a DOCR registry to/from clusters), clusterlint (run/fetch manifest-linting diagnostics), and cluster-user lookup — deliberately deferred; see Tech design § Reuse & cleanup and § Decisions made by DEV01 for why.
- Building a tool against DigitalOcean's `recycle_nodePool` endpoint — it is marked `deprecated: true` in DigitalOcean's own spec, which tells callers to use node delete-with-replace instead; this design uses the modern endpoint only (see Tech design § Option analysis).
- OAuth-based auth — DOKS uses a single bearer token (the same account-level token already used by Apps/Inference), so there is no authorization-code flow to support.
- A UI. This is a backend MCP connector; the only user-facing surface is the Agent Platform's existing generic connector chrome, which this ticket does not change.

### Acceptance criteria AC1..AC20

- **AC1**: Given the connector is running and a client sends `tools/list`, Then the response includes all 16 `digitalocean_kubernetes_*` tools (see Tech design § Change list), each with a description whose first line is ≤ 100 characters and whose full text is ≤ 500 characters, and each annotated with the correct `readOnlyHint`/`destructiveHint`/`idempotentHint`.
- **AC2**: Given a `tools/call` request that is missing the `X-DigitalOcean-Api-Token` header, When any Kubernetes tool is invoked, Then the response is HTTP 401 and the body lists the required header name — the request never reaches DigitalOcean's API.
- **AC3**: Given a valid token, When `digitalocean_kubernetes_list_clusters` is called with no arguments, Then it returns at most 50 clusters (default) with a `has_more` flag; When called with `limit=500`, Then it returns at most 200 (the hard cap) even if more exist upstream.
- **AC4**: Given a valid token and an existing cluster id, When `digitalocean_kubernetes_get_cluster` is called with no flags, Then it returns the cluster's spec, status, and node-pool summary; When called with `include_upgrades=true`, Then the response also includes the list of available target versions (empty list, not an error, if the cluster is already current); When called with `include_status_messages=true`, Then the response also includes recent lifecycle status messages; Given a cluster id that does not exist (or belongs to another account), Then the response is a structured `not_found` error, not an HTTP 500.
- **AC5**: Given a valid token and a cluster spec with at least one node pool, When `digitalocean_kubernetes_create_cluster` is called, Then DigitalOcean's own validation errors (e.g. invalid region/size/version slug) are surfaced as a structured `invalid_argument` error with DigitalOcean's message, not swallowed or turned into a generic failure.
- **AC6**: Given a valid token, an existing cluster id, and one or more fields to change, When `digitalocean_kubernetes_update_cluster` is called, Then only the supplied fields change and the tool's description documents this as a **partial update** (unlike DigitalOcean's App Platform `PUT`, which is a full-spec replace) — fields omitted from the call keep their current server-side value.
- **AC7**: Given a valid token, an existing cluster id, and an explicit target `version` slug (obtained from a prior `include_upgrades=true` call), When `digitalocean_kubernetes_upgrade_cluster` is called, Then the cluster's control-plane upgrade is triggered and the tool is annotated `destructiveHint: true` (disruptive maintenance operation); there is no "upgrade to latest" implicit default — `version` is required.
- **AC8**: Given a valid token and an existing cluster id, When `digitalocean_kubernetes_list_cluster_resources` is called, Then it returns the load balancers, volumes, and volume snapshots DigitalOcean associates with that cluster (id + name each), annotated `readOnlyHint: true` — intended to be called before a destructive delete.
- **AC9**: Given a valid token and an existing cluster id, When `digitalocean_kubernetes_delete_cluster` is called with `mode="plain"`, Then only the cluster itself is deleted and its associated load balancers/volumes/snapshots are left untouched; When called with `mode="selective"` and explicit `load_balancer_ids`/`volume_ids`/`volume_snapshot_ids` lists, Then only the cluster and the listed resources are destroyed; When called with `mode="dangerous"`, Then the cluster and **every** associated resource are destroyed; every mode is annotated `destructiveHint: true`, and the tool's description states that `mode="dangerous"` is irreversible and destroys more than the cluster itself. There is no default `mode` — the caller must choose one explicitly.
- **AC10**: Given a valid token and an existing cluster id, When `digitalocean_kubernetes_get_kubeconfig` is called, Then it returns the cluster's raw kubeconfig YAML; the token value and the returned kubeconfig content are never written to logs.
- **AC11**: Given a valid token and an existing cluster id, When `digitalocean_kubernetes_get_credentials` is called, Then it returns the structured credential bundle (API server URL, CA data, auth token, `expires_at`, and the legacy client-certificate fields when DigitalOcean returns them for an older cluster) rather than a YAML document — distinguishing it from `get_kubeconfig`'s format; the bundle is never written to logs; an optional `expiry_seconds` argument is forwarded to DigitalOcean when supplied.
- **AC12**: Given a valid token and an existing cluster id, When `digitalocean_kubernetes_list_node_pools` is called, Then it returns every node pool's name, size, count, labels, taints, autoscale configuration, and node summaries; When `digitalocean_kubernetes_get_node_pool` is called with a specific pool id, Then it returns that single pool with the same fields; an id that does not exist returns `not_found`.
- **AC13**: Given a valid token, an existing cluster id, and a pool spec (`name`, `size`, `count`, optionally `auto_scale`/`min_nodes`/`max_nodes`), When `digitalocean_kubernetes_create_node_pool` is called, Then DigitalOcean's own validation errors (e.g. `min_nodes`/`max_nodes` inconsistent with `auto_scale`) are surfaced as a structured `invalid_argument` error.
- **AC14**: Given a valid token, an existing cluster id and pool id, When `digitalocean_kubernetes_update_node_pool` is called to resize `count`, change `labels`/`taints`, or adjust the autoscale bounds, Then the pool is updated and the tool is annotated `idempotentHint: true` (repeating the same call converges to the same state, it does not add more nodes each time).
- **AC15**: Given a valid token, an existing cluster id and pool id, When `digitalocean_kubernetes_delete_node_pool` is called, Then it requires the explicit pool id (no name lookup, no "all pools"), is annotated `destructiveHint: true`, and its description states the action is irreversible.
- **AC16**: Given a valid token and explicit `cluster_id`/`node_pool_id`/`node_id`, When `digitalocean_kubernetes_delete_node` is called with `replace=false` (default), Then the node is drained (unless `skip_drain=true`) and removed with no replacement; When called with `replace=true`, Then DigitalOcean provisions a new node in the pool after removing this one — the tool's description states this is the modern equivalent of DigitalOcean's deprecated "recycle" operation; there is no bulk/"all nodes in pool" argument.
- **AC17**: Given a valid token, When `digitalocean_kubernetes_get_deployment_options` is called, Then it returns the available regions, Kubernetes version slugs, and node sizes with no required arguments, annotated `readOnlyHint: true, idempotentHint: true` — used to validate inputs before calling `create_cluster`/`create_node_pool`.
- **AC18**: Given two concurrent `tools/call` requests carrying two different tenants' `X-DigitalOcean-Api-Token` values, When both complete, Then neither response contains data retrieved using the other request's token — verified by a concurrency test asserting no shared mutable state keyed only by in-process globals.
- **AC19**: Given DigitalOcean's API returns `429` or a `5xx`, When a tool call is in flight, Then the connector retries with backoff honouring `Retry-After` up to the configured budget, and if the budget is exhausted, returns a structured `rate_limited` or `upstream_error` rather than hanging past the per-call timeout.
- **AC20**: Given the repository's `README.md`, Then it documents the single `X-DigitalOcean-Api-Token` header (reused from the Apps/Inference resource groups, not reintroduced), lists all 16 `digitalocean_kubernetes_*` tools in the tool table, and its "MSPbots Connector" section is byte-for-byte identical to `~/.claude/skills/vendor-mcp-development/reference/readme-connector-section.md`.

## Tech design

### Conclusion

Add a third resource-group module to `MSPbotsAIFramework/digitalocean-mcp` (Python 3.12 + `uv` + FastMCP, following the vendor-mcp-development SOP and the shared conventions already recorded by the Apps and Inference designs on this same still-empty repo): a thin DigitalOcean API client wrapping `https://api.digitalocean.com/v2/kubernetes*`, and 16 MCP tools that group DigitalOcean's 28 raw Kubernetes-tag endpoints into agent-facing capabilities (not a 1:1 endpoint mirror — same approach Apps already took). Credentials reuse the existing single Header, `X-DigitalOcean-Api-Token`, mapped to `Authorization: Bearer <token>` on every outbound call; nothing is cached across requests.

### Where the current implementation lives

Nothing exists yet on `main`: one commit, a 2-line `README.md` (34681e7) — confirmed via `prepare_repo.py` and a direct read of the worktree. This is a from-scratch build for this resource group (SOP "main line A" shape, though the repo itself is not brand-new — it already has two sibling designs targeting it). There is no DOKS implementation anywhere in MSPbotsAIFramework to pattern-match against (the earlier `[BLOCKED · vendor-mcp]` comment on this ticket, 2026-10-30, ran the full 129-repo org listing and found none). The closest shape references are: (a) the SOP's own template structure, and (b) the two sibling designs already on this repo (`dev/PRD-21338`, `dev/PRD-21343`), which this design follows for every shared decision (header name, tool-naming scheme, scaffolding module names) rather than re-deciding them.

### Option analysis

| Option | Approach | Pros | Cons | Verdict |
|---|---|---|---|---|
| Mirror DigitalOcean's 28 endpoints 1:1 as 28 tools | One MCP tool per API operation | Simplest mapping, no judgement calls | Exceeds the SOP's ≤ 20 tools/service reference metric on its own, and compounds an aggregate budget that is already over ceiling with just Apps + Inference (22) | Rejected — same reasoning Apps already applied, more acute here given the aggregate |
| Group into capability-shaped tools (chosen) | 16 tools; `get_cluster` absorbs the separate "available upgrades" and "status messages" reads as opt-in flags; `delete_cluster` absorbs the three destroy-variant endpoints (plain/selective/dangerous) behind one explicit `mode` argument | Each merged tool maps to one agent-recognizable action; cuts 28 raw operations down to 16 without losing any non-deferred capability; keeps this ticket's own addition in the same order of magnitude as Apps' 18 despite DOKS having a larger raw surface | Each merged tool has a slightly larger parameter surface (e.g. `delete_cluster` takes a required `mode` plus mode-dependent id lists) — documented per-tool, not hidden | **Chosen** |
| Build a tool against `kubernetes_recycle_node_pool` (`POST .../node_pools/{id}/recycle`) | Expose DigitalOcean's "recycle a node pool" endpoint as a tool | Matches the endpoint's name literally | DigitalOcean's own spec marks this endpoint `deprecated: true` and its description tells callers to use `DELETE .../nodes/{node_id}` instead; shipping a tool against a vendor-deprecated endpoint on day one is building something the vendor is already walking away from | **Rejected** — `digitalocean_kubernetes_delete_node`'s `replace=true` argument covers the same "swap this node for a fresh one" capability via the current (non-deprecated) endpoint |
| Defer container-registry integration, clusterlint, and cluster-user lookup to a follow-up | Ship 16 tools covering cluster/node-pool/node lifecycle, credentials, upgrades, and reference data now; leave registry attach/detach, clusterlint run/results, and cluster-user lookup for later | Keeps v1 scoped to "manage clusters and their node pools" (the ticket's own paraphrased ask); registry integration in particular is arguably a different resource group's concern (DOCR, not DOKS) rather than core cluster management; clusterlint is a developer code-quality tool orthogonal to live cluster operations; cluster-user lookup is low-value for an automated agent caller | Three DigitalOcean capabilities aren't reachable from day one | **Chosen** — additive later, no breaking change if added |

No framework alternative to FastMCP was considered in depth: the SOP mandates it for Python services, and both sibling resource groups in this same repo already adopted it — matching them is "reuse the organization's (and this repo's own) existing pattern," not a from-scratch choice (SOP A3; `templates-design.md` §3 selection order: reuse > open source > self-build).

### Reuse & cleanup

- **Reuse**: the credential Header name (`X-DigitalOcean-Api-Token`) and the `digitalocean_<group>_<verb>_<resource>` tool-naming scheme are reused verbatim from PRD-21338's design (and restated identically by PRD-21343), not reinvented. The `server.py`/`settings.py`/`middleware.py`/`errors.py` scaffold, and the `FastMCP` + `httpx` + `pydantic`/`pydantic-settings` stack, are shared infrastructure — this ticket does not duplicate them per resource group.
- **New dependencies**: none beyond what the shared scaffold already needs. No DigitalOcean-specific SDK is used, for the same reason PRD-21338 rejected `pydo`: it is synchronous and would fight FastMCP's async model and the SOP's per-request isolation requirement.
- **Module layout**: assumed `src/digitalocean_mcp/kubernetes/` subpackage with `clusters.py` / `access.py` / `node_pools.py` / `reference.py`, mirroring PRD-21343's assumed `inference/` subpackage shape (no code exists yet to confirm this against; whichever ticket's dev leg lands first in practice fixes the layout, and this and later tickets should follow suit rather than re-litigate it — same caveat PRD-21343 already recorded).
- **Interfaces**: all 16 tool functions take explicit keyword arguments (no positional id soup) and return a single compact JSON string per the SOP's return-shape rules (`ensure_ascii=False`, no `indent=2`, `limit`/`has_more` for every `list_*` tool). Tool parameters mirror DigitalOcean's own request fields (`name`, `region`, `version`, `size`, `count`, `auto_scale`, `min_nodes`, `max_nodes`, `labels`, `taints`, `skip_drain`, `replace`, etc.) rather than inventing MSPbots-specific names, so tool descriptions and DigitalOcean's own docs stay in sync. This is the first version of every signature in this module — there is nothing pre-existing to keep compatible with yet.
- **In-scope cleanup**: none — nothing exists yet in this resource group to clean up.
- **Suggested follow-ups** (out of this ticket, listed for product/future tickets, not acted on here): container-registry attach/detach tools (`kubernetes_add_registry`/`kubernetes_add_registries`/`kubernetes_remove_registry`/`kubernetes_remove_registries` — arguably belongs with a future Container Registry resource group rather than core DOKS management); clusterlint run/results tools (`kubernetes_run_clusterLint`/`kubernetes_get_clusterLintResults` — a manifest/code-quality tool, not a live-cluster operation); cluster-user lookup (`kubernetes_get_clusterUser` — low value for an automated caller). None of these are "unused code to delete" — they are DigitalOcean capabilities this first version deliberately does not expose.

### Data & API contract

**Credential header** (reused from the Apps/Inference resource groups, not reintroduced — declared to the MCP gateway at registration time, SOP §3.1):

| Header | Required | Type | Description |
|---|---|---|---|
| `X-DigitalOcean-Api-Token` | yes | password | DigitalOcean Personal Access Token (Control Panel → API → Tokens → Generate New Token). Needs read/write scope for the write tools; a read-only token works for the read-only tools and returns DigitalOcean's own 403 for write attempts. |

### Key flow / sequence

```
Agent (tenant) --tools/call(digitalocean_kubernetes_get_cluster, Header: X-DigitalOcean-Api-Token)--> Gateway
  --HTTP, Header forwarded--> digitalocean-mcp /mcp
    middleware: read Header -> ContextVar; missing -> 401 (AC2)
    tool: digitalocean_kubernetes_get_cluster(cluster_id, include_upgrades?, include_status_messages?)
      -> client.py builds Authorization: Bearer <token> from ContextVar
      -> GET https://api.digitalocean.com/v2/kubernetes/clusters/{cluster_id}
      -> if include_upgrades: GET .../upgrades (merged into the response)
      -> if include_status_messages: GET .../status_messages (merged into the response)
      -> on 429/5xx: retry with backoff honouring Retry-After, budget-bounded (AC19)
      -> map DigitalOcean response/error onto the tool's return shape / error envelope
    middleware: ContextVar reset() in finally, regardless of success/failure
  <-- compact JSON result or {"error": {...}} --
<-- tools/call result --
```

```
Agent --tools/call(digitalocean_kubernetes_delete_cluster, {cluster_id, mode: "dangerous"})--> ... /mcp
  tool: mode is required (no default) -> dispatch on mode
    mode="plain"      -> DELETE /v2/kubernetes/clusters/{id}
    mode="selective"  -> requires load_balancer_ids/volume_ids/volume_snapshot_ids -> DELETE .../selective
    mode="dangerous"  -> DELETE .../dangerous (destroys cluster + all associated resources)
  -> 204 from DigitalOcean -> tool returns {"deleted": true, "mode": "dangerous"}
  -> 404 -> not_found; 429/5xx -> retry/backoff as above (AC19)
```

### Non-functional

- **Idempotency & concurrency**: read tools (`list_*`/`get_*`) are naturally idempotent. `create_cluster`/`create_node_pool` are not idempotent — repeated calls create repeated resources, documented rather than papered over with client-side dedup (forbidden by the stateless requirement). `update_cluster`/`update_node_pool` are partial updates that converge to the same state on repeat (idempotentHint). `delete_*` tools are terminal: calling again after success returns DigitalOcean's own `not_found`, which is treated as an acceptable terminal state, not re-executed. `upgrade_cluster` called again when already at the target version surfaces DigitalOcean's own validation response as `invalid_argument` rather than a silently fabricated no-op.
- **Performance**: `list_clusters`/`list_node_pools` paginate per SOP (default ≤ 50, hard cap ≤ 200 — defensive for node pools, which rarely exceed single digits per cluster, but the guard is uniform across every `list_*` tool rather than cluster-count-dependent); `get_cluster`/`get_credentials` responses are size-bounded at 20,000 characters per SOP A4 **except** `get_kubeconfig`, whose raw YAML must never be truncated (a truncated kubeconfig is corrupt, not merely incomplete) — if a kubeconfig were ever to exceed the bound (not expected in practice; a typical DOKS kubeconfig is a few KB), the tool returns a structured `upstream_error` explaining the response was too large to return safely, rather than truncating it; one `httpx.AsyncClient` per process, reused across requests within a process, never across tenants' *data* — only the transport is shared.
- **Security**: credentials, kubeconfig content, and the credentials bundle are treated as equally sensitive as the bearer token itself — none of the three is ever logged, written to disk, or included in error messages; `gitleaks detect` run before delivery (SOP §11); destructive tools (`delete_cluster`, `delete_node_pool`, `delete_node`, `upgrade_cluster`) require an explicit resource id (and, for `delete_cluster`, an explicit `mode`), so there is no way to construct an accidental bulk-destructive call or silently land on the most destructive delete mode.
- **Multi-tenant isolation**: `contextvars.ContextVar` scopes the credential per request (set in middleware, `reset()` in `finally`, shared with the Apps/Inference resource groups); no module-level or global mutable state holds tenant data between requests (AC18); the `httpx.AsyncClient` instance carries no auth state — `Authorization` is attached per-outbound-call from the context var.
- **Observability**: structured logs include tool name, DigitalOcean operation, cluster/node-pool/node id when present, outcome, and latency; explicitly never include the token header value, kubeconfig content, or the credentials bundle.

### Rollout & rollback

No feature flag — this is a new tool group within a connector that does not exist in INT yet (the repo has never been registered). Rollout is the SOP's standard path: this resource group's code merges to `main` alongside whichever sibling groups have also landed → `uv run pytest` on the merged code → first-time registration is `/api/vendor-register` (handled once by whichever ticket's review leg merges+registers first; subsequent changes, including this group's own future changes, use `/api/deploy-int`) → INT health check → connector wiki update. If this group's tools misbehave after registration, revert this group's commit on `main` and redeploy — the other resource groups' tools are unaffected, since each group registers its own independent tool functions rather than sharing a toggle. DigitalOcean-side cluster "rollback" has no equivalent in Kubernetes the way App Platform has deployment rollback; there is nothing analogous to expose here.

### Risks & dependencies

- **Risk**: `get_kubeconfig`/`get_credentials` return artifacts that grant full cluster-admin access to whatever cluster they target — a bigger blast radius than any single Apps/Inference credential. Mitigation: never logged, never persisted, size-bounding exempts (rather than silently truncates) the kubeconfig case (§ Non-functional); destructive tools still require explicit ids so a leaked credential's *scope* is at least limited to the one cluster it was requested for.
- **Risk**: `delete_cluster(mode="dangerous")` is irreversible and destroys resources beyond the cluster itself (load balancers, volumes, snapshots). Mitigation: `mode` has no default (AC9), the tool is `destructiveHint: true`, and the description states the "dangerous" mode's blast radius explicitly rather than relying on the caller to infer it from the name.
- **Risk**: four tickets share one repository, one `dev-lock`, and (per PRD-21343's assumption, not yet confirmed) one shared `tools/list` registration. Mitigation: this ticket's dev leg takes the lock only for the duration of its own change, touches only the `kubernetes/` subpackage, `tests/kubernetes/`, and the shared scaffolding (`server.py`, `client.py`-adjacent patterns, `errors.py`, `middleware.py`, `settings.py`) that the other resource groups also need and should extend, not duplicate. As of this design, PRD-21338 and PRD-21343 are designed but not yet in development (`5c`/`6a`), so there is no concurrent-edit conflict today; whichever of the three lands first in the dev leg effectively fixes the module-layout and `server.py` registration pattern, and this ticket's dev leg should rebase onto it rather than recreate it.
- **Risk / flagged, not resolved here**: repo-wide tool budget (cross-referenced in Product design § Open questions) — Apps (18) + Inference (4) + this ticket (16) = 38 tools if registered as one shared connector, well past the SOP's ≤ 20 reference ceiling, before Networking (PRD-21345) contributes anything. This is a cross-ticket decision (trim one or more groups' tool counts, or register the four resource groups as separate MCP services instead of one shared connector, or accept the ceiling as not applicable to a deliberately multi-resource-group connector) that none of the three designed tickets can resolve alone; recorded consistently across all three so the review leg sees it explicitly.
- **Dependency**: none on another ClickUp ticket. Depends on DigitalOcean's public API remaining as documented (external, unversioned dependency common to every vendor MCP connector, not specific to this design).

## Decisions made by DEV01

No one was available to ask (unattended design tick), so the following first-version choices were made and are flagged here for product/engineering to revisit if wrong — changing any of them is a comment + move back to `5b - ready for groom`, not a silent edit:

- **Credential header: reuse `X-DigitalOcean-Api-Token` from PRD-21338's design rather than inventing a second header** — DigitalOcean's own account model uses one Personal Access Token across App Platform, Serverless Inference, and the Kubernetes Service API (all under `securitySchemes.bearer_auth`); since this repo's four resource-group tickets are framed by the org admin as one shared repo, one credential header keeps the connector to one credential form in the platform's Library UI. Alternative considered: a dedicated `X-DigitalOcean-Kubernetes-Token` header — rejected for the same reason PRD-21343 rejected a dedicated Inference header: it would force tenants to manage a second credential for what is, in DigitalOcean's own account model, a single account and a single token.
- **Tool naming: `digitalocean_kubernetes_<verb>_<resource>`** — follows PRD-21338's already-decided `digitalocean_<group>_<verb>_<resource>` scheme, restated identically by PRD-21343. Alternative considered: flat `digitalocean_<verb>_<resource>` — rejected for the same collision reason both prior designs already rejected it (e.g. a bare `digitalocean_list_options` here would collide with a differently-scoped options/reference tool in another resource group).
- **Module layout: assumed `src/digitalocean_mcp/kubernetes/` subpackage** — no code exists yet to confirm this against; mirrors PRD-21343's identical assumption for `inference/`. Alternative considered: flat `src/digitalocean_mcp/` with per-group filename prefixes — not chosen, consistent with PRD-21343's reasoning; whichever ticket's dev leg lands first effectively decides this.
- **Tool count and grouping (16 tools, not 28)** — chose capability-shaped tools over a 1:1 endpoint mirror, merging `get_cluster`+upgrades+status-messages and the three cluster-destroy variants into single parameterized tools, for the same reason Apps made the same call (stay within range of the SOP's ≤ 20 ceiling, keep `tools/list` from flooding with near-duplicate variants). Alternative considered: mirror all 28 endpoints — rejected, see Option analysis.
- **Excluded `recycle_nodePool`, not merely deferred** — DigitalOcean's own spec marks it `deprecated: true` and tells callers to use the current node-delete-with-replace endpoint instead; `digitalocean_kubernetes_delete_node`'s `replace=true` argument already provides the same capability through the endpoint DigitalOcean wants used going forward. Alternative considered: build it anyway for "completeness" — rejected as building against a vendor-deprecated endpoint on day one.
- **Deferred capabilities: container-registry attach/detach, clusterlint, cluster-user lookup** — excluded from v1 because the ticket's paraphrased ask is "manage clusters and their node pools," registry integration arguably belongs with a future Container Registry resource group rather than core DOKS management, clusterlint is a manifest/code-quality tool orthogonal to live cluster operations, and cluster-user lookup is low-value for an automated agent caller. Alternative considered: include everything now — rejected to keep the first version's scope proportional to the stated need, same reasoning Apps already applied to its own deferred list.
- **`delete_cluster` exposed as one action-style tool with a required `mode` argument (plain/selective/dangerous), not three separate tools** — avoids a generically-named "delete cluster" tool that an agent could call without realizing DigitalOcean offers a far more destructive variant under the same verb; making `mode` required and explicit (no default) puts the "dangerous" choice in the caller's hands every time, not just in the tool's name. Alternative considered: three separate tools (`delete_cluster`, `delete_cluster_selective`, `delete_cluster_dangerous`) — rejected as adding 2 extra tool-budget entries for a distinction that a single required argument already expresses clearly.
- **`PUT`-based `update_cluster` documented as a partial update, not a full-spec replace** — DigitalOcean's own description for this endpoint says to "specify one or more of the attributes," unlike App Platform's `PUT /v2/apps/{id}` (confirmed full-replace, per PRD-21338's design). Documenting the actual semantics per-endpoint (rather than assuming all `PUT`s in this connector behave the same way) avoids surprising callers who read DigitalOcean's own docs. Alternative considered: assume full-replace semantics identical to Apps' `update_app` — rejected as factually wrong for this endpoint.
